## 14C — Collection, display and income

Relevant code: `src/server/Data/ProfileDefaults.luau`, `ProfileSchema.luau`, `ProfileMigration.luau`, `ProfileService.luau`, `ProfileRepository.luau`; `src/server/Domain/TutorialDeliveryRules.luau`, `PublicDeliveryRules.luau`, `ExhibitArrangementRules.luau`, `BestPublicDisplays.luau`, `IncomeMath.luau`; `src/server/Services/DeliveryService.luau`, `ExhibitArrangementService.luau`, `IncomeService.luau`, `PlotService.luau`; `src/client/CollectionHud.luau`, `CashHud.luau`; `src/shared/ItemCatalog.luau`, `BalanceConfig.luau`. Existing domain tests include `tests/unit/Task13.spec.luau` and `TutorialLoop.spec.luau`.

Confirmed rules:

- A newly delivered tutorial toaster is already registered and placed on the protected stand by `TutorialDeliveryRules`; the schema keeps it there until its first displayed income. That stand is safe and earns half its catalog rate: $6/min from a $12/min base. The tutorial waits for the first $1 earned before public stock unlocks. Thus “automatic first-item display” exists for the tutorial item. If that item was saved but visually absent, inspect the saved `displaySlots.protected`, assigned museum sockets and `RegisteredDisplays` reconstruction before changing delivery rules.
- A first unique public item fills the first empty public stand and becomes approved. There are two public stands and one protected stand in the current tier-one layout. Once both public stands are occupied, newly registered items go to safe storage, stay owned, and earn $0 until displayed. A duplicate item gives salvage, not another exhibit. `DeliveryService` currently says “stored safely” or “displayed,” but the stored message does not offer a one-click remedy.
- Existing Auto mode is **Auto among approved public items**. `BestPublicDisplays` sorts available, approved owned items by catalog base income, then item ID for ties, and fills the two public slots. Switching Auto on while already in Auto returns `AlreadyAuto`; it does not approve stored items. Manual Place can choose protected/public stands; Store removes public approval and can leave an item stored. Replacing an item preserves ownership subject to storage capacity. Server arrangement requests are validated, rate limited, saved as operations, blocked during raid transfer locks, and settle old income before changing stands.
- Income comes only from currently displayed, available items. Public stands pay full catalog base income; protected pays the configured multiplier 0.5; stored/missing items pay zero. Catalog rarity affects item definitions and depot weights, but `IncomeMath` applies no separate rarity multiplier. The HUD uses the same displayed rate in $/minute. Do not label it $/second.
- The profile schema rejects unknown IDs, duplicate placements, invalid slots, unapproved public displays, unavailable items and storage overflow. `PlotService.RefreshDisplays` rebuilds physical models from saved slots and sockets; a saved slot with an unavailable/missing socket can create a visual mismatch that the player report alone cannot confirm.

Recommended narrow design:

1. Preserve the tutorial toaster rule. On the first public registration, keep the existing empty-stand placement. Investigate any report of that case failing as a specific persistence/visual reconstruction defect; do not overwrite a player's manual choice.
2. Add a distinct **Auto Equip Best** action. On the server, consider every **Available, owned, catalog-valid** exhibit once, including currently stored and unapproved items. Respect the protected tutorial toaster lock until the first-income step. Evaluate legal placements across the protected slot and two public slots using `IncomeMath.RatePerMinute` (full public rate, half protected rate), current available sockets, storage capacity, and any raid transfer lock. Use deterministic tie breaks: preserve current placement when income ties, then catalog ID/slot order. Never place one ID twice; never delete displaced items. If the existing approved-only Auto preference is retained, make this action deliberately approve selected public items and distinguish its label from “Auto: approved items.”
3. Submit one server-side arrangement operation with an idempotent request ID; settle old income first, validate the resulting profile with existing schema/capacity rules, save, then refresh physical displays. A failed save must leave the previous arrangement intact. Explicit manual Place/Store should switch to Manual and remain effective until the player presses Auto Equip Best again. Do not silently re-equip stored items on rejoin or after every delivery against Manual mode.
4. Show a compact Collection summary: owned/available, displayed/3, stored/capacity, and current museum income **$/min**. After a delivery stored because stands are full, give one short message: “Saved to Collection. Stands full—use Auto Equip Best or choose a stand.” If an item is saved but a display model fails to render, surface that separately from the economic slot state.

Dependency and regression checks: `BestPublicDisplays`/`ExhibitArrangementRules` (new deterministic action), `ExhibitArrangementService` (request/save/lock), `CollectionHud` and `DeliveryService` (button and feedback), `ProfileService` payload or derived UI summary, `PlotService` refresh. Preserve `ProfileSchema`, catalog rates, salvage, existing operation ID and protected first-income rule unless a test proves a narrow change is required. Test fresh first tutorial/public item, full stands, missing item, duplicate, manual override, maxed storage, failed save, rejoin, cross-player request, raid lock, protected income and no item loss.

## 14D — Tutorial

Relevant code: `TutorialCarryState`, `TutorialProgress`, `TutorialDeliveryRules`, `CarryService`, `DeliveryService`, `IncomeService`, `TutorialGuideController`, `TutorialPickupController`, `CollectionHud`, `GuardHud`, `NotificationHud`, `TutorialCarryState`/`TutorialLoop` tests, and `NpcRunFeedback`/`TutorialCarryState` protection. The existing flow is guided personal pickup → route arrow/return → protected delivery → wait for first earned dollar → public stock unlock. Replay uses the tutorial carry with no duplicate collection reward and guard protection; first-item protection is enforced server-side. Collection has an additional three-step, long-text Auto/Manual/storage walkthrough and a nudge after a public item. Guard has a separate optional help overlay and warning text. These layers can compete for attention even though the state machine is small.

Recommend keeping the state machine and shortening presentation to one guided heist with action-gated cues: **STEAL** (world marker and hold), **ESCAPE** (arrow, short guard/cover warning only when relevant), **DISPLAY** (receiving stand highlight; the protected toaster equips automatically), **EARN** (show the first $1 and $/min), **UPGRADE** (a brief Collection/stand choice tip after public delivery), **REPEAT** (next stock objective). Replace paragraphs and a required three-step Collection walkthrough with a dismissible, contextual one-action nudge. Do not add a new persistent tutorial step just to show text. Replay should reuse the existing replay flag and server idempotence, never register/pay twice or bypass first-item, stock or run-identity protections. The existing guard tip says hide for four seconds; verify/correct that wording against actual last-known-position search before displaying it to a beginner.

Test with an unfamiliar player on keyboard and phone: without instructions, can they explain where a saved item is, how to display it, why storage earns $0, and how to repeat a heist? Record hesitation, taps and repeated prompts. Rejoin at each tutorial boundary; replay after completion; disconnect during pickup/delivery; verify guard protection and unchanged rewards.

## 14E — Lobby wardrobe and shop

Relevant code: `src/lobby/LobbyWorld.luau`, `WardrobeService.luau`, `Bootstrap.server.luau`, `src/lobbyClient/Lobby.client.luau`; `src/shared/WardrobeUi.luau`, `WardrobeCatalog.luau`, `WardrobeAppearance.luau`; `src/matchShared/WardrobeSession.luau`, `WardrobeStore.luau`; `src/server/Services/WardrobeService.luau`, `src/server/Domain/WardrobePurchaseRules.luau`, `src/client/OperationsMenu.luau` and `Bootstrap.client.luau`; `lobby.project.json`/`default.project.json` and `docs/post-task12-wardrobe.md`.

The lobby **already** has `RobberWardrobeDisplay`, mirror, mannequin, wardrobe sign, hidden prompt anchor and `OpenWardrobe` proximity prompt. The lobby client already starts the shared Wardrobe UI; the prompt calls `WardrobeSession.Open`, which opens that same UI. The museum uses the same UI embedded in its Operations Menu. There is no need for a duplicate wardrobe implementation. Existing cash cosmetics and free items can be previewed/equipped in the lobby through the shared wardrobe record. Lobby purchases are deliberately disabled (`canBuy=false`): cash purchases commit to the museum profile only in the gameplay place, then owned cosmetics mirror into the shared wardrobe store. Lobby `profileOwned` reads the museum DataStore **without a lease**, solely to repair a missed owned-cosmetic mirror. The lobby must not mutate or charge that profile. Robux looks are preview-only and marked unavailable until later purchase tasks approve offers/IDs; there is no live Robux checkout to expose now. The Travel/Sprint menu is a separate future ability surface, not part of the wardrobe purchase service.

Plan: improve the existing locker sign to say **OPEN WARDROBE — TRY ON & EQUIP**; add a restrained glow/proximity highlight to the existing display and keep the current prompt. The prompt should continue calling `WardrobeSession.Open` and the shared UI. Show “Owned—Equip,” “Buy in museum” for unowned cash cosmetics, and “Preview—Unavailable” for Robux drafts. If immediate cash purchase in the lobby becomes a requirement, first build an explicit cross-place server transaction that owns the museum profile write and reconciles the wardrobe mirror; this is a separate dependency and should not be solved by charging an unleased lobby read or duplicating purchase logic. No new product or price is proposed.

Dependencies/regressions: `LobbyWorld` visuals/sign, `lobby/WardrobeService` prompt, `WardrobeUi` state labels, `WardrobeSession`/`WardrobeStore` and museum purchase operation. Test prompt reachability and visibility on phone/controller, outfit try-on/equip/remove/restore, locked states, lobby → museum → lobby ownership/loadout persistence, an unowned lobby cash purchase remaining disabled, DataStore failure/read-only lobby behavior, and a later approved cross-place purchase path only if implemented.
